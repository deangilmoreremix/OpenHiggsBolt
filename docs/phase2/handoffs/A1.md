## What this proves

Phase 1 proved the five Remotion designs render in the **live preview** (a Remotion `<Player>`). The unit
tests (`brandedRenderEvidence.test.ts`, `webExport.*.test.ts`) assert MP4 *properties* against a
**mocked** `@remotion/web-renderer`, so **no design had ever been baked into an actual encoded file**.
This agent closed that gap.

The new spec drives the **real production app** (`/personalization-demo?test=true` → Simple Mode →
Step 4), applies a Remotion design, and triggers the **real in-browser export**
(`@remotion/web-renderer` → WebCodecs `VideoEncoder` → a real MP4 on disk). It then decodes the
produced file back in the browser and asserts on the **encoded pixels**.

Three tests, all green, run against a production build that includes the current working tree
(A3's modal change and A4's inspector change are in the build that produced this evidence).

| # | Test | Proves |
|---|---|---|
| 1 | `the browser export produces a real encoded MP4 that contains the design` | the export writes a real, encoded MP4 (ISO-BMFF `ftyp`, H.264 `avc1` track, AAC `mp4a` track, 2,056,899 bytes, 1920×1080, 5.077333 s) and the composition the web renderer rasterized contained the design **and** the MIT credit line |
| 2 | `the design is in the encoded pixels, and the un-personalized render has none` | 13,348 brand-primary pixels inside the design's box in the personalized frame, **0** in the same box of the control frame; 17,315 changed pixels, **all** inside the design box (0 outside); 834 changed / 796 brighter pixels in the credit line's own rectangle |
| 3 | `every registered design exports to a real encoded MP4` | all five catalog designs (`animated-headline`, `logo-reveal`, `lower-third`, `promo-cta`, `visual-effect`) export to a real H.264/AAC MP4 of 1920×1080, each with its own design id and the MIT credit line in the exported composition's DOM |

## Decisions

- **Drove the real app instead of a standalone harness page.** The demo page is not gated:
  `access` defaults to `authenticated` and the "Render branded video" button is enabled, so the
  production export path (`src/shared/personalization/webExport.ts` → `renderMediaOnWeb`) is
  exercised exactly as a customer would exercise it. No harness, no mock.
- **Control = the identical composition with the design layer hidden** (the overlay inspector's
  "Hide Design" toggle), not a separately configured render. That isolates the design as the *only*
  difference between the two encoded files, which is what makes the pixel comparison meaningful.
- **The control runs in its own browser context.** The app persists the approved project (including
  the applied design id) into browser storage; a shared context restores that state and the design
  pill — which *toggles* — de-selects the design again. This cost me one debugging cycle; it is now
  encoded in the spec.
- **Captured the export through `URL.createObjectURL` interception** rather than the download event.
  The provider creates one object URL for the result panel and `downloadWebExportBlob()` creates a
  second one for the download anchor; both wrap the same Blob, so the last recorded `video/*` Blob is
  the export. This is deterministic and works for both the personalized and the hidden-design control.
- **Set the design's colour through the product's own colour input** (`input[aria-label="Text color"]`)
  to `#29d3f2`. See "Interface changes" for why the default colour is *not* the brand primary.
- **Asserted the "only difference" property as well as the brand-pixel count**, so a false positive
  (a coincidental cyan pixel in the source video) cannot satisfy the test: 0 of 17,315 changed pixels
  fall outside the design's box.
- **Wrote the raw MP4s to `test-results/remotion-export/`** (git-ignored) rather than into the repo,
  so the artifacts are inspectable after a run without bloating the branch. `e2e/fixtures/remotion-export/**`
  was **not** needed — the spec is self-contained and needs no fixture files.

## Interface changes (consumers must know)

- **`src/shared/personalization/preview/PersonalizationComposition.tsx` — the design's text colour is
  the brand TEXT colour, not the brand PRIMARY colour.** In the composition's design branch the
  colour handed to the design component is
  `layer.color ?? (layer.kind === 'cta' ? settings.brandColors.accent : settings.brandColors.text)`.
  A `design` layer has no `layer.color` of its own, so a design is painted in
  `brandColors.text` (default `#ffffff`), **not** `brandColors.primary` (`#29d3f2`). The design
  adapters read `pickColor([props.color, props.colors?.text])`, so `props.color` wins.
  *Consequence:* the premise that "`animated-headline` is drawn in the brand primary `#29d3f2`" is
  **false in the current code** — it is drawn in white unless the user picks a colour in the layer
  inspector. This spec works around it by setting the layer colour to `#29d3f2` through the product
  UI, and then proves the pixels are exactly that colour. **A11 should decide** whether designs are
  meant to default to `brandColors.primary`; if so, the `textColor` derivation for `kind === 'design'`
  in the composition is the one-line place to change. **I did not change it.**
- **No other source change is required** for the export to be provable. The export path, the
  composition, the registry and all five adapters work as they stand.

## What was NOT proven (honest limits)

- **The pixel-level proof is for `animated-headline` only.** The other four designs are proven to
  export to a real H.264/AAC MP4 with their design id and the MIT credit line in the exported
  composition's DOM, but their *pixels* were not colour-compared frame by frame (each design has its
  own palette and geometry, and the brand-primary assertion is specific to the headline design).
- **The comparison is against a control rendered by the same browser in the same session**, not
  against the source video file alone. The control *is* the source video plus the app's 18 % dim
  overlay, so the "the source video alone does not produce these pixels" claim is demonstrated
  empirically (0 brand-primary pixels in the control's design box) rather than by re-encoding the raw
  source.
- **One export was sampled at one frame (t = 2.0 s).** The design's whole visible window was not
  swept frame by frame; the sampled frame is inside the design's visible window and outside the end
  card's window, which is what the assertion needs.
- **A 1-pixel tolerance band is used around `#29d3f2`** (per channel ≤ 40 for the "is brand primary"
  test, ≤ 24 for the "changed" test) because the video pipeline is YUV 4:2:0 and the canvas
  conversion is not bit-exact. The mean of the matched pixels is within 5 of the target per channel,
  so the band is not doing any work the pixels do not already do.
- **`npm run test:unit` was NOT run** (the orchestrator runs it under a separate lock grant).
- **No commit was made.** The two new files are left in the working tree.
