## The two fixes

### Defect 1 — z-index collision with the Video Studio modal

**Change:** the modal root's stacking utility moved from `z-[100]` to `z-[250]`.

**The z-index scale actually found in the codebase** (surveyed with
`z-\[[0-9]+\]` over `src/` and `packages/studio/src/`; Tailwind arbitrary
values only — the repo also has a few inline `zIndex:` numbers in
`src/apps/vfx-studio/**`, which are a different, app-local layer):

| Value | Where |
|---|---|
| `z-[60]` | `src/apps/go-ai-viral/StudioTargetPicker.tsx:30` |
| `z-[80]` | `packages/studio/src/components/UniversalMediaUploader.jsx:327` |
| `z-[100]` | studio modals — `packages/studio/src/components/VideoStudio.jsx:3131`, `MarketingStudio.jsx:731`, `CinemaStudio.jsx:388` + `:1143`, `RecastStudio.jsx:1102`, `LipSyncStudio.jsx:1327`, `ImageStudio.jsx:2032`, `DrawModal.jsx:1070`, `WorkflowStudio.jsx:1167`; also `src/components/ImageStudio.js:1215`, `src/components/LipSyncStudio.js:347` |
| `z-[120]` | `src/components/DrawModal.js:10`, `src/shared/personalization/image-editor/ImageEditorModal.tsx:967` |
| `z-[200]` | `components/ApiKeyModal.js:43` (the API-key gate) |
| `z-[300]` | `src/access/UpgradeModal.tsx:77` (the upgrade / plan gate); also `packages/studio/src/components/MotionControlStudio.jsx:1413` |
| `z-[100]` (was) | `src/shared/personalization/PersonalizationModal.tsx:1438` — **collided with the studio modals** |

**Chosen value: `z-[250]`.** It is the only value in the band the audit
specified — strictly greater than the studio modals (`100`) and the API-key
modal (`200`), and strictly less than the upgrade gate (`300`). Raising the
modal to `300+` would have put it *above* the upgrade/plan gate, which is the
one overlay that must still be able to interrupt the user (it is how a
free-tier visitor is converted), so the band is the constraint and `250` is the
value inside it.

Note: `src/shared/personalization/image-editor/ImageEditorModal.tsx:967` is
`z-[120]` and is rendered *inside* the Personalization Modal, so it is not
affected by the modal's own layer.

### Defect 2 — body scroll-lock clobbered the previous value

**Change:** the previous inline `document.body.style.overflow` is captured in
a ref when the lock is taken, and that exact value is restored on cleanup —
including the empty string (unset) case.

The effect's dependencies (`isOpen`, `closePersonalize`,
`personalizationInProgress`, `imageEditorAsset`) mean it can re-run while the
modal stays open. React always runs the previous cleanup *before* the next
effect body, so the cleanup restores the captured value and the next run
re-captures the same value — the capture/restore pair is idempotent across
re-runs. The ref is nulled after the restore so a stale value can never be
written back.

### New test file

`src/shared/personalization/__tests__/PersonalizationModalRobustness.test.tsx`
— written in the "guards" style of `PersonalizationModalLayout.test.tsx`
(inspects the DOM, asserts concrete values, no snapshots, no UI driving). It
covers:

1. the modal root's z-index is `250` — strictly greater than the studio
   modal's `100` and the API-key modal's `200`, strictly less than the upgrade
   gate's `300`;
2. opening the modal with `document.body.style.overflow = 'auto'` and closing
   it restores `'auto'` **exactly**;
3. opening the modal with `document.body.style.overflow = ''` and closing it
   restores `''`;
4. **unmounting** the tree (not just closing) also restores the previous value.

Because jsdom does not load the app's Tailwind stylesheet,
`getComputedStyle(el).zIndex` is `''` for a class-driven `z-[N]` utility, so
the test reads the effective value from the element itself (inline
`z-index` if present, otherwise the `z-[N]` arbitrary utility in the class
list) via a documented `effectiveZIndex()` helper.

## Decisions

- **Modal root z-index = `z-[250]`.** Surveyed the real scale rather than
  trusting the audit's suggestion: the studio modals are `z-[100]`, the
  API-key gate is `z-[200]` (`components/ApiKeyModal.js:43`), the upgrade /
  plan gate is `z-[300]` (`src/access/UpgradeModal.tsx:77`). `250` is inside
  that band. Going to `300+` would put the Personalization Modal above the
  upgrade gate, which must stay able to interrupt the user.
- **Capture the previous overflow in a ref rather than in effect-local state.**
  The effect re-runs on `personalizationInProgress` / `imageEditorAsset`
  changes; a ref survives the re-run and React's cleanup-before-setup
  ordering makes the capture/restore pair idempotent across re-runs. The ref
  is nulled after the restore so a stale value can never be written back.
- **Restore with `previousBodyOverflowRef.current ?? ''`.** The `??` (not `||`)
  keeps the empty string intact — `''` is a legitimate "no inline overflow"
  value and `||` would have turned it into `''` anyway, but `??` states the
  intent (only `null`/`undefined` fall back) and makes the `null` sentinel
  unambiguous.
- **New test file rather than extending the layout guards.** The layout test
  is a geometry guard; the z-index + scroll-lock contract is a different
  concern with a different failure mode, and the task asked for a dedicated
  file.
- **Test reads the z-index from the class list, not `getComputedStyle`.**
  jsdom does not load Tailwind, so `getComputedStyle(el).zIndex` is `''` for
  `z-[N]`; the helper documents this and resolves the value the browser
  would compute.
