## 3. The font strategy: **(b) self-hosted font file**

### Evidence for (a) and why it was rejected

The app *does* already bundle a webfont:

- `app/layout.js:2` — `import { Inter } from "next/font/google";`
- `app/layout.js:9-12` — `const inter = Inter({ variable: "--font-inter", subsets: ["latin"] });`
- `app/layout.js:32` — `<body className={inter.variable}>`

Next.js downloads it from Google Fonts **at build time** and self-hosts it into
the build output. The generated CSS (`next build` → `.next/static/css/7b736202f0b1dbfd.css`) is:

```css
@font-face{font-family:Inter;font-style:normal;font-weight:100 900;font-display:swap;
src:url(/_next/static/media/ba9851c3c22cd980-s.woff2) format("woff2");unicode-range:u+0460-052f,…}
…
@font-face{font-family:Inter;font-style:normal;font-weight:100 900;font-display:swap;
src:url(/_next/static/media/e4af272ccee01ff0-s.p.woff2) format("woff2");
unicode-range:u+00??,u+0131,u+0152-0153,u+02bb-02bc,u+02c6,u+02da,u+02dc,u+0304,u+0308,u+0329,
u+2000-206f,u+20ac,u+2122,u+2191,u+2193,u+2212,u+2215,u+feff,u+fffd}
@font-face{font-family:Inter Fallback;src:local("Arial");ascent-override:90.44%;…;size-adjust:107.12%}
.__variable_d8ebd1{--font-inter:"Inter","Inter Fallback"}
```

Reusing it was rejected for four concrete reasons:

1. **It is not self-contained.** The binary lives in `.next/static/media/`, a
   *build artifact*. It is not a source-controlled asset, its URL carries a
   content hash that changes whenever the upstream font or the Next.js version
   changes, and it does not exist in any non-Next.js host (the Vite app at
   `src/main.js`, the Electron shell in `electron/`, the Remotion Studio). The
   same design would render with Inter in the Next.js app and with a system
   font everywhere else — the exact non-determinism we are removing.
2. **The build is not hermetic.** `next/font/google` fetches from Google
   Fonts during `next build`. A clean, offline or air-gapped build either
   fails or silently produces a build without the font.
3. **The fallback is a system font.** `font-family: Inter Fallback` is
   `src: local("Arial")` with metric overrides. If the real face has not
   loaded, the browser substitutes Arial — present on macOS and Windows,
   usually absent on Linux, where the generic substitute is chosen instead.
   The metrics are then *different* per machine. `font-display: swap` makes
   that window real.
4. **`next/font` is a Next.js-only construct.** The Remotion composition also
   runs in the Remotion Studio and in the Electron/Vite shell, where
   `--font-inter` and the hashed `@font-face` are undefined. A stack that
   starts with `var(--font-inter)` would resolve to the *inherited* value
   (serif) there, which is worse than the system stack it replaces.

### Why (c) is rejected

Option (c) is impossible, not merely unattractive. A "deterministic system
stack" does not exist: `-apple-system` resolves to SF Pro on macOS and to
nothing on Windows; `Segoe UI` exists on Windows and not on macOS; `Roboto`
is not installed by default anywhere; and the terminal `sans-serif` is
resolved by the OS (SF/Helvetica on macOS, Arial on Windows, DejaVu/Noto on
Linux). Two machines with the same stack produce different glyph outlines,
different advance widths and therefore different line breaks. This is
documented in §4 of `docs/phase2/handoffs/A10.md` and is why the fix had to
be a *bundled* face.

### What (b) means here

`public/fonts/personalization-sans-latin.woff2` is the **Latin subset of the
very same Inter build the app already ships** — the file Next.js produced at
`._next/static/media/e4af272ccee01ff0-s.p.woff2`, vendored into `public/` under
a stable, hash-free name. It was obtained legally (Google Fonts, SIL OFL 1.1),
and its provenance was verified by parsing the binary:

```

table directory: GDEF, GPOS, GSUB, HVAR, MVAR, OS/2, STAT, avar, cmap, fvar,

name table (UTF-16BE): "Inter Regular" / "Version 4.001;git-66647c0bb" /
```

`fvar` + `gvar` + `avar` + `HVAR` + `MVAR` + `STAT` prove it is the **variable**

The `cmap` was parsed to derive the exact `unicode-range` written into the

### Why the family is called "Personalization Sans" and not "Inter"

`app/layout.js` already registers a family called `Inter`. A stylesheet
injected *later* in the cascade wins over an earlier one for the same family
name, so reusing the name "Inter" would make the winner depend on stylesheet
order — non-deterministic in exactly the way we are removing. `Personalization
Sans` cannot collide with anything, so the bundled file is always the face
that is used. The test `never names the family "Inter", which the app already
registers` pins this.

## 4. How the frozen upstreams are overridden without editing them

The upstreams set `font-family` as an **inline style** on their own text
elements (`style={{ fontFamily: FONT_EN }}`). An inline style can only be
beaten from outside by a declaration with `!important`. `typography.ts`
therefore injects one stylesheet:

```css
@font-face {
  font-family: "Personalization Sans";
  font-style: normal;
  font-weight: 100 900;
  font-display: block;
  src: url("/fonts/personalization-sans-latin.woff2") format("woff2");
  unicode-range: …;
}

[data-remotion-design], [data-remotion-design] * {
  font-family: "Personalization Sans", Inter, ui-sans-serif, system-ui, sans-serif !important;
}
```

`[data-remotion-design]` is the attribute `designs/shared.tsx:223` puts on the
stage that wraps **every** upstream, so the rule is scoped to the design layer
and touches nothing else in the app.

The chain of custody from CSS to pixels was verified in the installed
`@remotion/web-renderer@4.0.499`:

- `dist/esm/index.mjs` — `drawText`: `contextToDraw.font = \`${fontStyle} ${fontWeight} ${fontSizePx}px ${fontFamily}\``,
  where `fontFamily` comes from `computedStyle` (i.e. `getComputedStyle`). So
  the overridden value is what the canvas paints with.
- `dist/esm/index.mjs` — `createScaffold`: the composition is mounted into a
  `div` that is `document.body.appendChild(wrapper)`-ed. **The scaffold lives
  in the main document**, so the page's stylesheets — including the injected
  `<style>` — apply to it. There is no shadow root and no iframe.
- `dist/esm/index.mjs` — `waitForReady` polls `scope.remotion_renderReady`
  before any frame is captured, and the scope is the renderer's own
  `delayRenderScope`.

### The render gate — why `useDelayRender()` and not `delayRender()`

This is the subtle part, and it is why `useDesignFonts()` is a hook.

`delayRender()` from `remotion` uses **`window`** as its scope:

```js
// node_modules/remotion/dist/esm/index.mjs — src/delay-render.ts
var delayRender = (label2, options) => {
  if (typeof window === "undefined") { return Math.random(); }
  return delayRenderInternal({ scope: window, environment: getRemotionEnvironment(), … });
};
```

The web-renderer does **not** wait on `window`. It creates its own scope and
publishes it through a React context:

```js
// node_modules/@remotion/web-renderer/dist/esm/index.mjs — createScaffold
const delayRenderScope = { remotion_renderReady: true, remotion_delayRenderTimeouts: {}, … };
root.render(jsx(Internals3.DelayRenderContextType.Provider, { value: delayRenderScope, … }));
```

and `useDelayRender()` is the only API that picks that scope up:

```js
// node_modules/remotion/dist/esm/index.mjs — src/use-delay-render.tsx
const scope = useContext(DelayRenderContextType) ?? (typeof window !== "undefined" ? window : undefined);
```

So a plain `delayRender()` would set `window.remotion_renderReady = false`,
which the web-renderer never reads — the export would capture frames with
fallback glyphs. `useDesignFonts()` uses `useDelayRender()`, so the handle
belongs to the render that is actually running, and `waitForReady` blocks
until it is closed.

### Failure handling (font cannot be loaded)

`loadDesignFonts()` **never throws**. It resolves to
`{ loaded: false, error: '…' }`, `useDesignFonts()` logs one `console.warn`
and closes the delay handle anyway. Consequences:

- the render is never stalled and the export is never empty;
- the text still renders, through `Inter` → `ui-sans-serif` → `system-ui` →
  `sans-serif` (the chain ends in a generic family, so there is always
  something to draw);
- the degradation is visible in the console, so it is diagnosable.

## 7. The font licence and the attribution obligation

**Font:** Inter 4.001 (variable, `wght` 100..900), Latin subset.
**Licence:** SIL Open Font License 1.1.
**Copyright:** Copyright 2016 The Inter Project Authors (<https://github.com/rsms/inter>).
**Licence text shipped with the binary:** `public/fonts/OFL.txt` (4 376 bytes,
sha256 `7fbb0605bb42e9ea50dc4d7856290d8f049a24c6fcebb9e01c12581a2e528eba`).

### What OFL 1.1 obliges us to do

OFL 1.1 §PERMISSION & CONDITIONS, clause 2:

> Original or Modified Versions of the Font Software may be bundled,
> redistributed and/or sold with any software, **provided that each copy
> contains the above copyright notice and this license**. These can be
> included either as stand-alone text files, human-readable headers or in the
> appropriate machine-readable metadata fields within text or binary files as
> long as those fields can be easily viewed by the user.

Concretely, this repo now owes the following:

1. **The licence must travel with the font.** `public/fonts/OFL.txt` carries
   the full OFL 1.1 text with Inter's copyright line on line 1. It sits in the
   same directory as the binary, so every copy of the font that ships in the
   build is accompanied by the licence. **The file must not be deleted,
   moved out of `public/fonts/`, or excluded from the deployment.** The
   typography test `ships the licence next to the font` guards this.
2. **The copyright notice must be reproduced.** It is on line 1 of
   `public/fonts/OFL.txt`. The binary itself also carries it in its `name`
   table (`Copyright 2016 The Inter Project Authors`), so the notice is
   present in both the human-readable and the machine-readable form OFL 1.1
   allows.
3. **The font may not be sold by itself** (clause 1). We bundle it with the
   app and never distribute it standalone — satisfied. Note this is a
   *different* obligation from the MIT credit line the designs already carry:
   `DESIGN_VIDEO_CREDIT` (`designs/shared.tsx:46`) covers the **upstream
   template's** MIT licence, not the font's OFL.
4. **No derivative may use a Reserved Font Name** (clause 3). Inter reserves
   the "Inter" name. **This is precisely why the bundled family is called
   "Personalization Sans" and not "Inter"** — see §3. The file is an
   unmodified copy, so it is an "Original Version" and the clause does not
   even bite; but the family name must not present itself as "Inter" either,
   because the upstream `next/font` copy in `app/layout.js` is a separate
   build artefact of the same font.
5. **The font must not be advertised as endorsed** (clause 4). We do not
   claim Inter's authors endorse the product.
6. **The font must be distributed entirely under OFL 1.1** (clause 5). The
   binary is unmodified; no subsetting or renaming of the file was performed
   (the Latin subsetting was done upstream by Google Fonts/Next.js before it
   was vendored).

### Attribution the product may want to show

The OFL does **not** require a visible credit line in the rendered video —
only that the notice and licence accompany the copies of the font. So the
designs' existing credit line does not have to change. If A11 wants to be
explicit about it, the natural place is the same `REMOTION_DESIGN_ATTRIBUTION`
/ `REMOTION_DESIGN_LICENSE_NOTICE` surface `templates/catalog.ts` already
exposes for the upstream MIT licence:

```
Design templates: MIT (© 2026 Trimora Inc. / RenderComp) · Typeface: Inter (SIL OFL 1.1) © 2016 The Inter Project Authors
```

That is a product decision, not a licence requirement — A11's call.

### No new licence obligation was created for the *code*

`typography.ts` and `designs/fonts.ts` are ordinary repo source and inherit the
repo's own licence. The new obligation is exclusively the font's.

## 8. Open questions / blockers

- **RESIDUAL-1 — the SVG badge monogram in `logo-stroke-draw` is still
  machine-dependent.** `LogoStrokeDraw.tsx:170` renders the monogram as an SVG
  `<text>` element. `@remotion/web-renderer` rasterises every `<svg>` element
  by serialising it with `XMLSerializer` and loading it as
  `data:image/svg+xml` (`dist/esm/index.mjs`, `turnSvgIntoDrawable` → `new
  Image()`). That isolated document cannot load a document-level `@font-face`,
  so the monogram falls back to a generic family inside the raster and its
  outline still depends on the OS. The live DOM is fine — the jsdom check
  shows the computed `font-family` of the `<text>` element *is* our stack —
  but the rasteriser only sees the `font-family` **presentation attribute**,
  which the serialiser copies verbatim. **This is pre-existing behaviour, not
  a regression** (the monogram already used the system stack inside the
  raster), and it affects one letter in one design. The real fixes are
  (a) render the monogram as an HTML element instead of SVG text, or
  (b) convert the glyph to outlines — both are design-layer changes outside
  A10's ownership. **Recommend A11 file this as a follow-up for the
  `logo-stroke-draw` design**; do not let it block the deterministic
  typography work.
- **The free overlay text layers are still system stacks** (see §2, last two
  tables). `presets.ts:254-275` offers Inter/Georgia/Impact/Monospace, all of
  which resolve per machine. Making *those* deterministic means bundling four
  more typefaces (or dropping the picker to the one bundled face). A10 left
  them alone deliberately — the picker is a customer-facing choice, not the
  design layer, and `presets.ts` is in A11's `core` lane. §5 Change 4 is the
  cheap partial step.
- **The `@font-face` is not preloaded.** The browser only fetches the font
  when the design layer is first rendered. Because `useDesignFonts()` is
  called from `DesignStage`, the font is loaded as soon as a design appears
  in the preview, i.e. long before the user presses Export, and the HTTP cache
  keeps it for the export. If A11 wants to remove even the first-paint
  latency, add to `app/layout.js`:
  `<link rel="preload" href="/fonts/personalization-sans-latin.woff2" as="font" type="font/woff2" crossorigin />`.
  A11 owns `app/layout.js`? It is not in any ownership row — A11 is the
  last writer for the integration, so it is A11's call. **Not required.**
- **The Remotion Player does not wait on `delayRender` handles.** The Player
  bundle contains no reference to `remotion_renderReady`, so the very first
  preview frame can briefly show the fallback family while the 48 KB face is
  still arriving. The export never does, because the web-renderer *does*
  wait. The preview and the export therefore converge within a few
  milliseconds and are identical by the time the export runs. If A11 wants a
  hard gate on the preview too, await `document.fonts.ready` before mounting
  the Player — but note that would delay the first preview paint, which is
  the worse trade.
- **No blockers.** A10's deliverables are complete and self-contained; the
  change A11 must apply is two small edits to one file.

## 9. Decisions

- **Ship a self-hosted variable Inter subset under `public/fonts/`** — it is
  the only option that is self-contained, hermetic and identical on every
  machine and in both render paths. The app's own `next/font` Inter is not
  reusable (build artifact, Next-only, build-time Google Fonts fetch, and its
  fallback is `local("Arial")`).
- **Name the family "Personalization Sans", not "Inter"** — the app already
  registers "Inter" through `next/font`, and OFL 1.1 clause 3 reserves the
  name for derivatives. A distinct name removes the cascade race and the
  reserved-name question in one move.
- **Override the frozen upstreams with `!important`, not by editing them** —
  the upstreams are frozen by contract; an inline style can only be beaten
  from outside by `!important`; and the selector is scoped to
  `[data-remotion-design]`, so nothing outside a design is affected.
- **Use `useDelayRender()` (the hook), not `delayRender()` (the function)** —
  only the hook picks up the web-renderer's own delay scope, so only the hook
  actually holds the export open until the font is ready.
- **`font-display: block`** — while the face loads the browser paints nothing
  rather than fallback glyphs, so a frame can never be captured with a mixture
  of two typefaces. The render is gated on the load anyway, so the invisible
  window is only the download itself.
- **A failed font load degrades, it does not abort** — the delay handle is
  always closed, the export is never empty, and the failure is logged once.
- **Only the design layer was changed** — the customer's free-text font picker
  is a product feature with system stacks by design; making it deterministic
  is a separate, larger piece of work (§8).
- **No npm dependency was added** — no `@remotion/google-fonts`, no
  `@fontsource/*`. The font is a vendored binary.
