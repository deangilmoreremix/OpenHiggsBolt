## Decisions

- **Reused V1's production build instead of rebuilding.** V1 released the lock at 04:04 EDT with
  `.next/BUILD_ID` written at 02:40 EDT; `find src components packages/studio/src app -newer
  .next/BUILD_ID` returned nothing, so the build was current. Rebuilding would have burned ~2.5 min
  of a loaded box for no evidence gain.
- **Started my own `next start` on port 3111.** The Playwright config's `webServer` command starts
  the broken `--turbopack` dev server; the config's `reuseExistingServer: true` makes Playwright
  use the already-listening production server instead.
- **Ran everything with `--workers=1`.** Required by the spec on a loaded box; the host had also
  settled (load 7.8–33 vs V1's 329–543) by the time the lock was released.
- **Read the 19 design ids from the registry source at run time** instead of hard-coding them.
  The spec parses `src/shared/personalization/templates/catalog.ts` and
  `.../designs/rveCatalogEntries.ts` (the two modules the registry registers from), asserts the
  count is 19, and then cross-checks the parsed list against the chips the running app renders — so
  a design that is registered but not surfaced (or surfaced but not registered) fails the spec.
- **Proved the studio hand-off with real assets.** The studios' media is seeded through the
  studios' own persistence keys (`hg_video_studio_persistent`, `hg_image_studio_persistent`) — the
  exact localStorage state a real upload leaves behind — using an mp4 and a jpeg the app itself
  serves, so real bytes are loaded rather than placeholders.
- **Signed in through Clerk's own flow (`@clerk/testing`'s `clerk.signIn`) rather than the
  cookie-only session mint alone.** The cookie-only mint (`e2e/fixtures/clerkSession.ts`) produces a
  session the *server* trusts but the *client* does not: on a Clerk dev instance the dev browser
  reports `"sessions": []`, so `useAuth().isSignedIn` is `false` and the entitlement gate
  (`requireEntitlement`) always denies. `clerk.signIn` uses the Backend API's sign-in ticket and
  produces a real client session. The repo's `installClerkAuth` fixture is installed **as well**,
  so the app's own `/api/personalization/**` calls carry the `Authorization: Bearer` header
  instead of 401-ing.
- **Stubbed `**/api/access/resolve` to `state: "paid"`** so the SmartVideo GO gate opens
  deterministically without a live Supabase entitlement row. The consequence — that row 10 does
  not exercise the live entitlement path — is stated in `docs/phase2/E2E_EVIDENCE.md` and in the
  spec header.
- **Did not touch the studio media for the other eight studios.** Only Video Studio and Image
  Studio were driven in the browser; the other eight are covered by a source-level wiring
  assertion. Driving all ten was not required by the brief ("at least Video Studio and one other
  studio") and each extra studio needs its own persistence key and media shape.

Personalization Modal logs a **400 `MISSING_PROJECT_ID`** from
`app/api/personalization/project/route.ts` — the durable "restore saved project" call never
works.

  `loadProject({ sourceId: src.id })`.
* `src/shared/personalization/supabaseProjectPersistence.ts:191-197` only sets the `id` search
  param when a `projectId` is supplied; `sourceId` is used client-side only (line 230). The request
  therefore goes out with **no query params**.
* `app/api/personalization/project/route.ts:64-65` reads only `id` and `list` → validation stage →
  **400** (line 109).

**Pre-existing proof:** `git diff --name-only 84a9d1586 --` returns nothing for those three files,

visitor's localStorage mirror, so the modal still opens (row 10 passes), but the **durable
